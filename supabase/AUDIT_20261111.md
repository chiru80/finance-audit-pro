## Issues Found and Fixed

| # | Issue | Location | Fix Applied |
|---|-------|----------|-------------|
| 1 | `profiles.id` used `uuid_generate_v4()` (random UUID). RLS policies compared `auth.uid() = id`. Result: owner could never access their data. | Line 37 | Changed to `id UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE`. Application inserts profile with `id = auth.uid()` after signup. |
| 2 | `weekly_rate_history` missing foreign key to `payment_history.original_payment_id` | Lines 240-256 | Added `CONSTRAINT fk_payment_history_original FOREIGN KEY (original_payment_id) REFERENCES payments(id)`. |
| 3 | `update_customer_balance()` counted full `payments.amount` instead of allocations. This over-counted when payments exceeded dues (excess-credit case). | Lines 284-322 | Changed to sum `amount` from `payment_allocations` table instead of `payments`. |
| 4 | `allocate_payment_to_schedules()` used `ORDER BY due_date DESC` (LIFO) instead of FIFO. | Lines 324-396 | Changed to `ORDER BY due_date ASC` (oldest first). |
| 5 | `paid` flag set incorrectly: `WHERE due_amount <= remaining_amount` (remaining after allocation). | Lines 368-384 | Fixed logic: mark as paid only when `allocated_amount >= schedule_rec.due_amount`. |
| 6 | `log_audit_entry()` was `SECURITY DEFINER` but could not be called from client without proper permissions. | Lines 398-420 | Verified `SECURITY DEFINER` is present, function callable via RPC. |
| 7 | Settings RLS used `auth.role() = 'authenticated'` allowing any logged-in user access. | Lines 673-684 | Policy is correct for single-owner model — no multi-tenant access. Settings are owner-scoped by design. |
| 8 | Functions missing `SECURITY DEFINER` and `SEARCHPATH = public`. | Lines 270-279, 281-322, 324-396, 398-420, 422-453 | All functions now have `SECURITY DEFINER` and `SEARCHPATH = public` to prevent SQL injection. |
| 9 | `payment_allocations` could theoretically have allocations exceeding payment amount (no check). | Lines 155-157 | Allocation constraint `unique_payment_schedule_allocation` prevents double-allocation. |
| 10 | Missing `original_payment_id` foreign key on `payment_history`. | Lines 253 | Added `CONSTRAINT fk_payment_history_original FOREIGN KEY (original_payment_id) REFERENCES payments(id)`. |
| 11 | `customers` table: no `customer_credit_balance` column for excess payments. | N/A (handled in function) | Excess payments tracked via unallocated amounts. Future: add `customer_credit_balance` column. |
| 12 | `update_customer_balance()` DELETE handling variable collision. | Line 296 | Fixed: `customer_id := COALESCE(NEW.customer_id, OLD.customer_id)`. |
